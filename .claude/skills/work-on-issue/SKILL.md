# Issue 実装作業コマンド

GitHub Issue・PR の参照・更新には `gh` コマンドを使用すること。対象リポジトリはカレントディレクトリの Git リモートから判定される。

## 入力

`$ARGUMENTS` から対象の Issue 番号を取得する。`#123` 、`123` のいずれの表記も許容する。番号が取得できない場合はユーザーに確認する。

## 手続き

### 1. Issue の取得

```bash
gh issue view <番号>
```

本文・ラベル・状態 (Open/Closed) を取得する。

### 2. draft ラベルの確認

`draft` ラベルが付与されている場合、詳細化が済んでいない可能性が高い。この場合、まず detail-issue による詳細化を先に行うかどうかを AskUserQuestion でユーザーに確認する。

詳細化を行う場合、Agent ツールで `general-purpose` サブエージェントをフォアグラウンド (`run_in_background: false`) で起動し、対象 Issue 番号を伝えたうえで detail-issue スキルの手続きを実行するよう指示する (サブエージェントのプロンプト内で Skill ツールにより `detail-issue` を呼び出させる)。コンテキストが肥大化するのを避けるため、詳細化と実装作業 (本手続きの3以降) を同一セッション内で連続実行してはならない。

サブエージェントの完了後、詳細化の結果 (更新されたドキュメント・作成された PR の URL など) を要約してユーザーに報告し、**本手続きはここで終了する**。実装作業を続ける場合は、詳細化用 PR のマージ・Issue の `draft` ラベル除去を確認したうえで、改めて本コマンドを実行するようユーザーに促す。

`draft` ラベルが付与されていない場合は、そのまま手順3へ進む。

ラベルの定義・付与基準は [Issue ラベル運用規約](../../../docs/dev-docs/content/project-rules/issue-labels.md) を参照。

### 3. 事前確認

以下のいずれかに該当する場合、既に対応済み・作業中の可能性があるため、AskUserQuestion で続行するかどうかをユーザーに確認する。

- 対象 Issue が Open でない
- ローカルまたはリモートに `topic/issue-<番号>` ブランチが既に存在する
- `.claude/worktrees/issue-<番号>` ワークツリーが既に存在する
- `topic/issue-<番号>` を head ブランチとする未マージの PR が存在する (detail-issue によるドキュメント更新 PR がまだマージされていない場合など)

続行しない選択がなされた場合はここで終了する。

### 4. ブランチ・ワークツリーの準備

`git status` で作業ツリーの状態を確認したうえで、[CONTRIBUTING.md](../../../CONTRIBUTING.md) のブランチ戦略に従い、最新化した `develop` から `topic/issue-<番号>` の形式でトピックブランチを作成する。CLAUDE.md の方針に従い、`.claude/worktrees/issue-<番号>` に Git Worktree を作成して作業を分離する。

### 5. TC の参照

`docs/dev-docs` で `npm run search:tc` ([TC についての運用ルール](../../../docs/dev-docs/content/technical-concerns/index.md) を参照) を実行し、その標準出力 (Open な TC 一覧、[opened-index.mdx](../../../docs/dev-docs/content/technical-concerns/opened-index.mdx) と同等の Markdown テーブル形式) を読み込み、次の流れで関連する TC を特定する。

- 対象 Issue のタイトル・本文のキーワードと、TC の各エントリーにおけるタグ・トリガー条件を照合する (`npm run search:tc -- --query=<キーワード>` で絞り込んでもよい)
- 関連が認められる TC があれば、個別ファイルを読み込む

Open な TC が存在しない、または関連する TC がない場合はこの手順をスキップする。

### 6. 実装・レビューサイクル

detail-issue で詳細化された受け入れ条件を満たすまで、実装とレビューを繰り返す。実装エージェントとレビューエージェントに別途依頼する形とし、本セッションはそのオーケストレーションを行う。

このサイクルは **最大5回** を1バッチとする。5回のループ内に受け入れ条件を満たさなかった場合、AskUserQuestion でユーザーに継続するかどうか確認する。継続する場合は、さらに5回のループを同様に行う (バッチを跨いでも指摘の履歴は次のループへ引き継ぐ)。

#### 実装エージェント

Agent ツールで `general-purpose` サブエージェントを起動する。プロンプトには以下を含める。

- 対象 Issue の本文 (目的・スコープ・受け入れ条件)
- 作業対象のワークツリーの絶対パス
- 手順5で特定した関連 TC の内容 (あれば)
- 2周目以降は、直前のレビューエージェントによる指摘事項

実装エージェントには、次のルールを守ることを明示的に指示する。

- [コーディング規約](../../../docs/dev-docs/content/project-rules/coding-styles.md) に従う
- [開発作業フロー](../../../docs/dev-docs/content/project-rules/workflow.md) の方針に従い、記録する価値がある設計判断は ADR として記録する ([ADR 運用ルール](../../../docs/dev-docs/content/adr/index.mdx) を参照)
- [CONTRIBUTING.md](../../../CONTRIBUTING.md) のコミットメッセージ規約に従い、ワークツリー内でコミットまで行う

#### レビューエージェント

実装エージェントの作業が完了したら、Agent ツールで `work-on-issue-reviewer` サブエージェント (`.claude/agents/work-on-issue-reviewer.md`) を起動し、作業が完了したワークツリーのレビューを依頼する。プロンプトには対象 Issue の受け入れ条件とワークツリーの絶対パスを含める。

レビューエージェントは PASS/FAIL を返す。FAIL の場合、指摘事項を次ループの実装エージェントへの入力に追加して手順6を繰り返す。

レビューの過程で TC 候補 (「現時点では対応不要だが、将来的に対応が必要になりうる懸念事項」に相当するもの) が挙がった場合、手順7まで記録しておく。

### 7. TC の記録

実装・レビューサイクルの中で TC の候補として懸念事項が挙がっている場合、[TC の記録基準](../../../docs/dev-docs/content/technical-concerns/index.md) に照らして次のように扱う。

- 記録すべき事項に該当する場合、[TC の書式](../../../docs/dev-docs/content/technical-concerns/index.md) に従い、新規の TC ファイルを作成する (Frontmatter で `status: open`・`trigger_summary` を設定すれば一覧への反映はビルド時に自動的に行われるため、`opened-index.mdx` へ手動で追記してはならない)
- TC・ADR・Issue のいずれとすべきか判断に迷う場合、実装・レビューエージェントの判断のみで確定させず、AskUserQuestion でユーザーに確認する
- 記録すべきでない事項 (現状の実装のまま受け入れられるが理由を明記しないと誤って削除・簡略化されるおそれがある注意点) に該当する場合、TC は作成せず、該当コードへの NOTE コメント追記と、レビューエージェントへの「要確認事項」としての提示にとどめる

TC の候補が挙がっていない場合は、この手順はスキップする。

### 8. push とローカル CI 実行

ここまでの変更をすべて push したのち、ワークツリー内で `./tools/ci/bin/check-all.sh` を実行し、その終了コードで成否を判定する。実行が長時間に及びうるため、Bash ツールのタイムアウトに依存せず、`run_in_background` でバックグラウンド実行して完了通知を待つ。

```bash
./tools/ci/bin/check-all.sh
```

終了コードが非 0 (FAIL) の場合、修正サイクルとして手順6に戻る。このリトライは手順6のバッチとは **独立してカウント** し、最大5回を1バッチとする。5回のループ内に成功しなかった場合、AskUserQuestion でユーザーに継続するかどうか確認する。

### 9. PR の作成とユーザーレビュー

Issue のタイトルと開発内容から PR のタイトル・本文を構成し、`develop` 向けの通常 (非 Draft) PR を作成する。

```bash
gh pr create --base develop --title "..." --body "..."
```

本文には [開発作業フロー](../../../docs/dev-docs/content/project-rules/workflow.md) の必須記載項目 (目的・変更内容・影響範囲・テスト観点) を含める。関連 Issue は、この PR が Issue の受け入れ条件を実質的に満たすものであるため `Closes #<番号>` と記載する (`develop` ベースの PR では実際には自動クローズされないため、手順11で改めて手動クローズする)。

変更されたファイルは change log を見れば自明であるため、PR の本文としては「なぜ」「どんな変更をしたか」の概要レベルで列挙して記述する。

PR 作成後、作成された PR の番号と URL をともなって次の内容をユーザーに報告し、レビュー・マージを求める。

- 実装内容
  - Issue の目的・受け入れ条件
  - 追加・更新された ADR
  - 変更ファイル数
  - 追加されたテストケース数
- CI の結果
- 追加・更新された TC
- 要確認事項 (あれば記載。なければ記載なし)

### 10. フィードバック対応

ユーザーのレビュー結果として修正が必要な場合、まずフィードバックに対して不明瞭な点・追加で決定すべき点がないかを精査し、議論を済ませたうえで手順6に戻る。

### 11. 後処理

PR のマージ報告を受けたら、一通り完了したものとして以下を行う。

- ローカルの `develop` を最新化する
- 作業ブランチ (`topic/issue-<番号>`) と対応するワークツリー (`.claude/worktrees/issue-<番号>`) を削除する
- Issue 本文の受け入れ条件チェックリストのうち満たしている項目をすべてチェックする (`gh issue edit` を使用する)
- `gh issue close <番号>` で Issue をクローズする

## 実行範囲に関する補足

detail-issue スキルと同様、手順4以降 (ブランチ・ワークツリー準備、実装/レビューサイクル、TC 記録、CI 実行、PR 作成、後処理) は、手順2・3・6・8で明示している AskUserQuestion による確認ポイントを除き、追加の確認を挟まず連続して自動実行すること。CLAUDE.md の「大規模な変更 (200行以上) を行う場合には、その前にまず変更計画を提案する」というルールは、本コマンドの実行範囲においては適用しない。
