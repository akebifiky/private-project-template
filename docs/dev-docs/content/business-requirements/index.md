# ビジネス要求について

ビジネス要求は、「なぜ (Why) 」この機能やふるまいが本プロジェクトの開発対象のシステムに必要かを定義するドキュメント群です。
本プロジェクトの開発ドキュメントは、次の 3 層で構成されます ([ADR-0007](../adr/ADR-0007-three-layer-dev-docs.md) を参照) 。

| 層   | 名称                                          | 定義する内容                                |
| ---- | --------------------------------------------- | ------------------------------------------- |
| Why  | ビジネス要求 (本ドキュメント)                 | なぜ必要か (ステークホルダーの必要性) |
| What | [システム要件](../system-requirements/index.md) | システムが何をするか                        |
| How  | [システムデザイン](../system-design/index.md)   | どのように実現するか                        |

ビジネス要求は、システム要件の源泉となります。
システム要件は、ビジネス要求を満たすために必要なシステムのふるまいとして、 EARS 書式で定義します。

## 運用ルール

- ビジネス要求は、業務領域 (システムが担う業務上の目的の単位) ごとに 1 ファイルへ分割し、肥大化を避ける。業務領域は、「同一の Why を満たす手段は 1 つの業務領域にまとめる」ことを基準とする
- ステークホルダーの必要性は、ビジネス要求に内包して記述する (ステークホルダー要求は別の層として扱わない)
- 1 つのユーザーストーリーには 1 つのロールを記載し、ロールが異なる必要性は別のビジネス要求として記述する
- 各ビジネス要求は、後述の「ユーザーストーリーの書式」に従って記述する
- ユーザーストーリーの主体 (「〜として」) には、 [ロール](./roles.md) で定義したロール名を用いる
- ビジネス要求 ID は `BR-<業務領域略称>-XXX` (3 桁ゼロ埋め、業務領域内連番) の形式とする (例: `BR-SOME-AREA-001`)
- ビジネス要求を削除する場合、当該 ID は欠番として扱い、再利用・再割当を行わない (削除理由は各業務領域ファイルのビジネス要求一覧に明記する。業務領域ごと廃止した場合は、本ページの「廃止した業務領域」に明記する)
- ビジネス要求は「なぜ (Why) 」必要かを定義するものとし、システムが「何を (What) 」行うかはシステム要件に、「どのように (How) 」実現するかはシステムデザインに委ねる
- 各ビジネス要求には、満たすためのシステム要件の ID (`SR-<ドメイン略称>-XXX`) を「関連するシステム要件」として明記し、ビジネス要求 → システム要件 → システムデザインのトレーサビリティを維持する
- 未決定の論点があるビジネス要求には、関連する GitHub Issue へのリンクを補足として明記する

## ユーザーストーリーの書式

ビジネス要求は、次のユーザーストーリー書式で記述します。

> &lt;ロール&gt; として、 &lt;理由・得られる価値&gt; &lt;目的・達成したいこと&gt; したい。

- ロールには、 [ロール](./roles.md) で定義したロール名を記載する
- 理由・得られる価値は、目的・達成したいことの前に置き、読点 (、) で区切る。 1 つの節で簡潔に書き、長くなる場合は備考へ移す
- 理由・得られる価値の末尾は、次のパターンから文として自然なものを選ぶ
- 特定の画面・コンポーネント・実装方式 (How) には言及しない

| パターン | 書式 | 用途 | 例 |
| --- | --- | --- | --- |
| 〜ため (動詞句) | &lt;解消・実現したいこと&gt; ため、 | 負担・手間・リスクの低減や、状態の実現 | 「利用者として、認証情報を新たに管理する負担をなくすため、普段使っているアカウントでログインしたい。」 |
| 〜のため (名詞句) | &lt;価値を表す名詞句&gt; のため、 | 価値を名詞で簡潔に表せる場合 | 「担当者として、業務の効率化のため、申請状況を一覧で確認したい。」 |
| 〜できるよう | &lt;可能にしたい状態&gt; できるよう、 | 目的の結果として、できるようにしたいことがある場合 | 「利用者として、必要な書類をすぐに入手できるよう、書類を種類ごとに探したい。」 |

上記のいずれも自然に書けない場合は、目的・達成したいことの記述を見直してください。

### テンプレート

業務領域ごとのファイルは、次の構成で記述します。

```markdown
# <業務領域名> (<業務領域略称>)

## 概要

<業務領域の概要と、システムが当該業務領域を担う理由>

## ビジネス要求一覧

| ID | ビジネス要求 | 関連するシステム要件 |
| --- | --- | --- |
| [BR-XXX-001](#br-xxx-001) | <ビジネス要求の要約> | [SR-YYY-001](../system-requirements/ドメイン名.md#sr-yyy-001) |

## ビジネス要求詳細

### BR-XXX-001 <ビジネス要求の要約> {#br-xxx-001}

<ロール> として、 <理由・得られる価値> <目的> したい。

- 関連するシステム要件: SR-YYY-001
- 備考: <補足事項>
```
