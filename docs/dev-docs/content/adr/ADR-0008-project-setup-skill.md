# ADR-0008: テンプレート適用後のプロジェクト設定を setup-project スキルで確定する

- Status: Accepted
- Date: 2026-11-07
- Decision Makers: Yoshioka

## Context

テンプレートは複数のプロジェクトで共通に使えることを目的としており、プロジェクトによって判断が分かれる項目 (例: E2E テストの要否、 Docusaurus の URL 、 UI デザインのルール) は、テンプレートレベルでは定められない。
現状は README の「テンプレート適用後の調整ポイント」に利用者が手作業で置き換える旨を記載しているのみで、確定すべき項目に漏れが生じうる。
適用後にプロジェクト側で決める項目を、 Claude Code のスキルを通じて漏れなく確定させる仕組みが必要である ([Issue #31](https://github.com/akebifiky/private-project-template/issues/31)) 。

あわせて、 [Issue #30](https://github.com/akebifiky/private-project-template/issues/30) (テスト仕様の追加) は、このスキルの存在を前提に、プロジェクトで定める項目を `testing.md` へ示す。
また、使用言語に応じた出し分けは [Issue #24](https://github.com/akebifiky/private-project-template/issues/24) で生成時に行う方針であり、本スキルと役割が重複しうる。

## Decision

### スキルの位置づけと名称

- `setup-project` スキルを、デフォルトテンプレート (`templates/default/.claude/skills/setup-project/SKILL.md.eta`) へ追加する
- 名称は、 CLI の `apply` ([ADR-0006](./ADR-0006-scaffold-template-structure.md)) と、避けた経緯のある `init` の双方と混同しないよう `setup-project` とする
- 既存スキルと同様、コマンドの名指し (`/setup-project`) または明示的な依頼があったときのみ起動する
- 本リポジトリ自身は初期化の対象ではなく、スキルの誤実行を避けるため、ルート直下の `.claude/skills/` へは複製しない (`CLAUDE.md` の「必要に応じて両方」に沿った判断)

### 確定する項目の宣言と検出

- プロジェクトで定める項目は、スキルへ固定で持たせず、各ドキュメントが「プロジェクトで定める項目」の見出しで宣言する。項目を追加する際にスキルを修正せずに済み、スキルとドキュメントの二重管理を避けられる
- 未確定の箇所には、本文中に `<!-- TODO(setup-project): 説明 -->` のマーカーを置く。スキルは `grep` でマーカーを検出し、利用者と対話して確定したうえで、マーカーを削除または確定内容へ置換する
- 初期化の完了は、マーカーが 0 件であることで判定し、スキルが `grep` の結果を報告する。再実行は、残っているマーカーから再開する (状態ファイルは持たない)

### 対象とする項目

| 項目 | 内容 |
| --- | --- |
| README の調整ポイント | Docusaurus 設定 (URL・組織名・アイコン画像) 、 `ui-design.md` 、 README の概要 |
| テスト仕様 | `testing.md` の「プロジェクトで定める項目」 (項目の追加は #30 で行う) |
| Git サービスのラベル | [Issue ラベル運用規約](../project-rules/issue-labels.md) で定めるラベルの作成 |
| ビジネス要求・ロール・システム要件 | 初期定義の Issue を起票するかのみ確認し、希望があれば `draft` ラベルで起票する (ドキュメント自体は編集しない) |

次の項目は対象外とする。

- 使用言語の選択 (使用しない言語の規約・設定の削除) : 生成時の出し分けを扱う #24 に委ねる。スキルとの二重の仕組みを避けるためである
- CI の位置づけ: `ci-mode` が生成時に確定しており、計測ツールの選定は `testing.md` の項目として #30 で扱う

### Git サービスのラベル

- 作成するラベルは、 [Issue ラベル運用規約](../project-rules/issue-labels.md) の「ラベルの分類」の表から取得し、 `gh label list` / `glab label list` で不足を特定する
- 不足するラベルは、利用者に一覧を提示して確認を得たうえで `gh label create` / `glab label create` で作成する。ラベルの作成は Git サービス上の変更であるため、確認なしには実行しない
- 説明文は同規約の各ラベルの節から要約し、色はスキルの既定とする。名称・色・説明文の正は Git サービス上の設定であり、規約の方針 (「Git サービス上の設定を正とする」) を変えない
- 利用者が使用しないとしたラベルは作成せず、規約の該当する記述を削除する (規約に定める「使用しないラベル」の扱いに従う)

### 変更の反映

- トピックブランチで編集して PR/MR を作成し、変更をレビューできるようにする ([開発作業フロー](../project-rules/workflow.md)) 。ラベルの作成のみ、 Git サービス上の操作として直接行う

## Consequences

- 適用後に決める項目が、ドキュメントの未確定マーカーとして可視化され、完了を機械的に判定できる
- 項目の追加はドキュメント側の宣言のみで済む。一方で、未確定マーカーの記法を守る運用がテンプレートの各ドキュメントに課される
- 言語選択を #24 に委ねるため、 #24 が未実装の間は、使用しない言語の規約の削除は利用者の手作業となる
- ラベルの色・説明文は、 Git サービスの既定ではなくスキルの既定となる。利用者は作成後に Git サービス上で調整する
- 本リポジトリにスキルを複製しないため、本リポジトリ自身では実行して挙動を確認できない。生成結果のスナップショットテストと、生成物の検査で確認する
