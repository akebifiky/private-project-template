# ADR-0003: 技術的懸念 (TC) を独立したドキュメント種別として管理する

- Status: Accepted
- Date: 2026-07-10
- Decision Makers: Yoshioka

## Context

開発作業の完了レポートでは「要確認事項」として、現時点では問題がないが将来的に問題になりうる設計上・実装上の懸念事項が報告されることがある。

こうした事項は個別の Issue に紐づくのではなく、複数の開発作業を横断して参照・評価される性質を持つ。一方で Issue はある作業の完了をもって閉じられるものであり、「将来の状況次第で対応が必要になりうる懸念」を追跡する仕組みとしては適合しない。

また、既存のドキュメント種別 (ADR・要求仕様・システム設計) との関係を整理すると:

- ADR は「下した設計判断の記録」であり、懸念事項とは性質が異なる
- 要求仕様・システム設計は Issue より上位の概念であるが、懸念事項を収容する構造を持たない

これらの課題に対応するため、懸念事項を体系的に管理するための新たなドキュメント種別の必要性が生じた。

## Decision

**技術的懸念 (TC: Technical Concern)** を独立したドキュメント種別として定義して管理する。

TC は以下のように位置づける:

```
要求仕様 → ADR → システム設計 → 開発作業 (Issue)
                      ↑
         TC (懸念として記録。上記いずれかに解決される)
```

TC の詳細な定義・運用ルール・テンプレートは `docs/dev-docs/content/technical-concerns/README.md` に記載する。

### ライフサイクル

TC は **Open** / **Resolved** の 2 状態で管理する。Resolved の出口種別として `Issued`・`Documented`・`Accepted` の 3 種を定義する。

### インデックス設計

TC の数が増えた場合のコンテキスト消費を抑えるため、Open TC のみを一覧する軽量なインデックスファイル (`opened-index.md`) を設ける。各エントリは ID・概要・タグ・トリガー条件の要約のみを保持し、詳細は個別ファイルに委ねる。

### 開発作業への統合

各開発作業の開始時に `opened-index.md` を参照して関連 TC を特定し、作業終了時に要確認事項から TC ファイルを自動生成する。

## Consequences

**期待効果:**

- 複数の開発作業をまたいで懸念事項を追跡・評価できるようになる
- 開発作業の開始時に関連する既知の懸念を参照でき、見落としを防ぐ
- 「現時点では対応しないが将来対応が必要になりうる」という状態を明示的に表現できる

**トレードオフ:**

- TC ファイルの作成・更新という管理コストが生じる
- インデックスの鮮度を保つため、Resolved 時に opened-index.md を更新する運用が必要
