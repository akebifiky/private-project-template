# TC について

## 1. 目的

**技術的懸念 (TC: Technical Concern)** は、「現時点では対応不要だが、将来的に対応が必要になりうる懸念事項」を記録し、追跡可能にするためのドキュメントです。開発作業の中に限らず、将来的に影響しうると判断した時点でいつでも起票してよいものとします。

本プロジェクトでは、ドキュメントと Issue を以下の階層で管理しています:

```
要求仕様 → ADR → システム設計 → 開発作業 (Issue)
```

TC はこの階層において、個別の Issue に紐づくのではなく、複数の開発作業を横断して参照される上位の概念として位置づけられます。ADR が「下した設計判断の記録」であるのに対し、TC は「将来の状況次第で対応が必要になりうる懸念の記録」です。

TC の解決 (Resolved) は、次のいずれかの形で行われます:

- Issue を起票して後続の開発作業として引き渡す
- ADR またはシステム設計ドキュメントを整備して設計上の根拠を記録する
- 制約として許容・確定し、アクションなしとしてクローズする

## 2. 記録基準

TC として記録するかどうかを都度判断すると、記録の粒度がぶれやすい。以下の基準を目安として、記録の要否を判断する。

### 記録すべき事項

次のいずれにも該当する場合は、 TC としての記録を検討する。

- 対応内容が未確定である
- 現時点では対応の必要がないが、将来的に何らかの対応が必要になりうる

### 記録すべきでない事項

次のいずれかに該当する事項は、原則として TC 化の対象外とする。

- 現状の実装のまま受け入れられる (仕様として確定している) が、理由を明記しないと誤って削除・簡略化されるおそれがある実装上の注意点 (コード上の NOTE コメントとして記載し、レビュー依頼時に「要確認事項」として提示するにとどめる)
- 対応内容が明確に定まっている事項 (TC ではなく Issue として起票する)
- 複数のコンポーネント・将来の意思決定に影響する設計判断 (TC ではなく [ADR](../adr/index.mdx) としての記録を検討する)

### 懸念の粒度

同じトピックを扱う懸念であっても、起点となる作業 (Issue やセッション) が異なる場合は、それぞれ別の TC として起票してよい。ただし、将来 Issue 化した際の作業スコープが複数機能にまたがらない程度に、懸念の対象を絞る。

## 3. 運用ルール

- 1 つの懸念事項につき 1 ファイルを作成する
- ファイルは本階層 (`dev-docs/content/technical-concerns/`) 配下に配置する
- ファイル名は `TC-XXXX-<kebab-case-title>.md` の形式とする (例: `TC-0001-notifier-validation-omission.md`)
- 連番は 4 桁のゼロ埋めとし、既存の最大番号の次の番号を使用する
- タグは kebab-case で記述する
- Open 状態の TC は、Frontmatter `status: open` を設定するだけで `opened-index.mdx` の一覧へビルド時に自動的に反映される (ADR-0159) 。一覧ファイル自体への手動での追記は不要であり、行ってはならない
- Resolved となった TC は、Frontmatter `status` を `resolved` に変更するだけで一覧から自動的に除外される。個別ファイルには解決情報を記録する
- 実装作業を開始する際は、必ず TC を棚卸しを行い、現在の作業スコープと関連するタグ・トリガー条件を持つ TC の個別ファイルを読み込む。Web ページ (`/technical-concerns/opened-index`) を閲覧するか、AI エージェントの場合は `npm run search:tc` (`docs/dev-docs/scripts/search-tc.ts`) の実行結果を参照する。棚卸しの際、トリガー条件を満たしていると判断される TC があれば、 Issue 化を検討する
- 新たな TC を作成する前に `dev-docs/content/technical-concerns/` を検索し、同様の懸念がすでに Resolved となっていないか確認することを推奨する
- メジャーバージョン (例: `1.0.0`) を確定させる前には、その時点で Open な TC すべてを対象に棚卸しを実施する。個別の実装作業に紐づく棚卸し (前項) とは異なり、トリガー条件の成否だけでなく、現状の実装を踏まえて懸念の前提自体が消失していないかも確認し、該当する TC は Resolved (Accepted) として記録する。棚卸しの実施結果 (確認日・対象件数など) は個別 TC ファイルや一覧には記録せず、棚卸しを行った Issue/PR 側の記述にとどめる

## 4. ステータス一覧

| ステータス | Frontmatter 上のコード | 意味                                               |
| ---------- | ---------------------- | -------------------------------------------------- |
| `Open`     | `open`                 | 記録済み・監視中。トリガー条件をまだ満たしていない |
| `Resolved` | `resolved`             | 解決済み。出口の種別を記録してクローズ             |

Resolved の出口種別 (resolution) と選択基準:

| 種別         | Frontmatter 上のコード | 選択基準                                                                              |
| ------------ | ---------------------- | ------------------------------------------------------------------------------------- |
| `Issued`     | `issued`               | TC の内容に基づいて、対応内容 (修正作業) が明確になった                               |
| `Documented` | `documented`           | 注意事項レベルであり、 ADR やシステム設計ドキュメントとして整備すれば十分と判断できる |
| `Accepted`   | `accepted`             | 上記いずれにも該当せず、議論を経て仕様として吸収することとした                        |

## 5. インデックス (opened-index.mdx)

`opened-index.mdx` は Open 状態の TC 一覧を表示する Web ページです。掲載内容は `dev-docs` のビルド時 (Docusaurus プラグイン `src/plugins/adr-tc-index` の `loadContent`/`contentLoaded`) に、本階層配下の各 TC ファイルの Frontmatter (`status`・`id`・`title`・`tags`・`trigger_summary`) を走査して動的に構築される (ADR-0159) 。ページ本体・一覧のいずれもファイルへの書き込みを伴わないため、`status: open` の TC ファイルを追加・変更するだけで一覧へ反映され、`status` を `resolved` に変更するだけで一覧から除外される。

### 表示形式

一覧は次の形式の Markdown テーブルと同等の内容で表示される (実際の描画は `src/components/OpenTcIndexList` が行う) 。

```markdown
| ID                            | 概要       | タグ       | トリガー条件 (要約)     |
| ----------------------------- | ---------- | ---------- | ----------------------- |
| [TC-0001](TC-0001-example.md) | 懸念の概要 | tag1, tag2 | トリガー条件の 1 行要約 |
```

### 表示項目

| 項目                | 説明                                                                | 取得元 Frontmatter |
| ------------------- | ------------------------------------------------------------------- | ------------------ |
| ID                  | TC ページへのリンク (`TC-XXXX` 形式)                                | `id`               |
| 概要                | 懸念の内容を 1 行で要約したもの                                     | `title`            |
| タグ                | 影響するコンポーネント・レイヤーなどを示すキーワード (カンマ区切り) | `tags`             |
| トリガー条件 (要約) | どのような状況で問題になるかを 1 行で示したもの                     | `trigger_summary`  |

`trigger_summary` は `status: open` の TC すべてに設定が必須であり、欠落は CI の lint ステップ (`npm run lint:adr-tc`、`tools/ci/bin/check-docs.sh`) で検知される。

### AI エージェントによる参照

AI エージェントがビルドを介さずファイルとして直接参照する場合は、`npm run search:tc` (`docs/dev-docs/scripts/search-tc.ts`) を実行し、その標準出力 (Web ページと同等の Markdown テーブル形式) を参照する。`work-on-issue` スキルの手順「5. TC の参照」を参照。

## 6. 書式 (テンプレート)

```markdown
---
id: TC-XXXX
title: タイトル
status: open / resolved
date: YYYY-MM-DD
tags:
  - tag1
  - tag2
trigger_summary: トリガー条件の1行要約 (status: open の場合は必須。opened-index.mdx の一覧・search:tc の出力に使用される)
resolution: issued / documented / accepted
resolved_at: YYYY-MM-DD
---

# TC-XXXX: タイトル

- Status: Open
- Date: YYYY-MM-DD

## 懸念の内容

何が懸念されているか

## 現状の前提条件

なぜ現時点では問題にならないのか

## トリガー条件

どのような状況になったら問題になるか。以下のいずれかの形で記述する (参考):

- コンポーネント起点: 「〇〇 コンポーネントを変更する作業が発生したとき」
- 状態起点: 「〇〇 のような実装パターンが現れたとき」

## 解決 (Resolved 時に記入)

- Resolution: Issued / Documented / Accepted
- Resolved at: YYYY-MM-DD
- Note: 解決の詳細 (関連する Issue・PR・ADR などへの言及は、末尾に別セクションを設けず、この Note や本文中の該当箇所に直接リンクとして埋め込む)
```

参照する Issue/PR/他ドキュメントは、本文中の該当箇所で直接リンク形式で記載する。本文中に登場しない関連資料がある場合は、末尾に `## 関連リンク` セクションを設けて記載する。
