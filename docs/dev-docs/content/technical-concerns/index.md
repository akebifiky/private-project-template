# TC について

## 1. 目的

**技術的懸念 (TC: Technical Concern)** は、開発作業の中で生じた「現時点では問題がないが、将来的に問題になりうる設計上・実装上の懸念事項」を記録し、追跡可能にするためのドキュメントです。

本プロジェクトでは、ドキュメントと Issue を以下の階層で管理しています:

```
要求仕様 → ADR → システム設計 → 開発作業 (Issue)
```

TC はこの階層において、個別の Issue に紐づくのではなく、複数の開発作業を横断して参照される上位の概念として位置づけられます。ADR が「下した設計判断の記録」であるのに対し、TC は「将来の状況次第で対応が必要になりうる懸念の記録」です。

TC の解決 (Resolved) は、次のいずれかの形で行われます:

- Issue を起票して後続の開発作業として引き渡す
- ADR またはシステム設計ドキュメントを整備して設計上の根拠を記録する
- 制約として許容・確定し、アクションなしとしてクローズする

## 2. 運用ルール

- 1 つの懸念事項につき 1 ファイルを作成する
- ファイルは本階層 (`dev-docs/content/technical-concerns/`) 配下に配置する
- ファイル名は `TC-XXXX-<kebab-case-title>.md` の形式とする (例: `TC-0001-notifier-validation-omission.md`)
- 連番は 4 桁のゼロ埋めとし、既存の最大番号の次の番号を使用する
- Open 状態の TC はすべて `opened-index.md` に記載する
- Resolved となった TC は `opened-index.md` から削除し、個別ファイルに解決情報を記録する
- 開発作業の開始時には `opened-index.md` を参照し、現在の作業スコープと関連するタグ・トリガー条件を持つ TC の個別ファイルを読み込む
- 新たな TC を作成する前に `dev-docs/content/technical-concerns/` を検索し、同様の懸念がすでに Resolved となっていないか確認することを推奨する

## 3. ステータス一覧

| ステータス | Frontmatter 上のコード | 意味                                               |
| ---------- | ---------------------- | -------------------------------------------------- |
| `Open`     | `open`                 | 記録済み・監視中。トリガー条件をまだ満たしていない |
| `Resolved` | `resolved`             | 解決済み。出口の種別を記録してクローズ             |

Resolved の出口種別 (resolution):

| 種別         | Frontmatter 上のコード | 意味                                             |
| ------------ | ---------------------- | ------------------------------------------------ |
| `Issued`     | `issued`               | Issue を起票して後続の開発作業として引き渡した   |
| `Documented` | `documented`           | ADR またはシステム設計ドキュメントとして整備した |
| `Accepted`   | `accepted`             | 制約として許容・確定した (アクションなし)        |

## 4. インデックス (opened-index.md)

`opened-index.md` は Open 状態の TC 一覧を管理する軽量なインデックスファイルです。開発作業の開始時に参照し、現在の作業スコープと関連する TC を絞り込むために使用します。

### 記載形式

```markdown
| ID                            | 概要       | タグ       | トリガー条件 (要約)     |
| ----------------------------- | ---------- | ---------- | ----------------------- |
| [TC-0001](TC-0001-example.md) | 懸念の概要 | tag1, tag2 | トリガー条件の 1 行要約 |
```

### 記載項目

| 項目                | 説明                                                                |
| ------------------- | ------------------------------------------------------------------- |
| ID                  | TC ファイルへのリンク (`TC-XXXX` 形式)                              |
| 概要                | 懸念の内容を 1 行で要約したもの                                     |
| タグ                | 影響するコンポーネント・レイヤーなどを示すキーワード (カンマ区切り) |
| トリガー条件 (要約) | どのような状況で問題になるかを 1 行で示したもの                     |

Resolved となった TC は `opened-index.md` から削除する。

## 5. 書式 (テンプレート)

```markdown
---
id: TC-XXXX
title: タイトル
status: open / resolved
date: YYYY-MM-DD
tags: tag1, tag2
resolution: issued / documented / accepted
resolved_at: YYYY-MM-DD
---

# TC-XXXX: タイトル

- Status: Open
- Date: YYYY-MM-DD

## 懸念の内容

何が懸念されているか

## 現状の前提条件

なぜ現時点では問題にならないのか

## トリガー条件

どのような状況になったら問題になるか。以下のいずれかの形で記述する (参考):

- コンポーネント起点: 「〇〇 コンポーネントを変更する作業が発生したとき」
- 状態起点: 「〇〇 のような実装パターンが現れたとき」

## 解決 (Resolved 時に記入)

- Resolution: Issued / Documented / Accepted
- Resolved at: YYYY-MM-DD
- Note: 解決の詳細 (Issue 番号、ADR 番号、許容の理由など)

## References

関連する Issue, PR, ADR など
```
