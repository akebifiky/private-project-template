# Issue ラベル運用規約

以下では、本プロジェクトの GitHub 上で管理する Issue に付与するラベルの定義・付与基準について定めます。

ラベルそのものの追加・変更 (名称・色・説明文) は GitHub 上で行うため、本ドキュメントの記載内容と GitHub 上の設定が異なる場合は GitHub 上の設定を正としてください。本ドキュメントは、各ラベルの付与基準や使い分けといった、 GitHub の UI だけでは伝わりにくい運用方針を補足するものです。

## ラベルの分類

本プロジェクトでは、目的の異なる 3 種類のラベルを組み合わせて Issue を分類します。

| 分類       | 説明                                                                | 対象ラベル                                                                              |
| ---------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| 種別ラベル | Issue が扱う作業の性質を示す。原則として 1 つの Issue に 1 つ付与する | `bug`, `design`, `documentation`, `enhancement`, `ops`, `plan`, `refactor`, `security` |
| 状態ラベル | Issue の進行状況を示す。作業の進行に応じて付与・除去する            | `draft`, `wip`, `pending`                                                               |
| 横断タグ   | 種別・状態とは独立した軸で、種別ラベルと併用する                    | `ai`                                                                                    |

## ラベルの用意

GitHub のリポジトリには、 `bug` / `documentation` / `enhancement` などのラベルが既定で用意されています。 `design` / `ops` / `plan` / `refactor` / `security` / `draft` / `wip` / `pending` / `ai` は既定では存在しないため、プロジェクトの開始時に、リポジトリの Issues 画面の Labels から追加してください。

プロジェクトで使用しないラベル (例: UI を持たないプロジェクトにおける `design`) は、追加を省略しても構いません。その場合、本ドキュメントの該当する記述を削除してください。

## 種別ラベル

Issue が扱う作業の性質に応じて、以下から 1 つを選んで付与します。複数の性質を併せ持つ場合は、その Issue が最終的に達成したい目的に最も近いものを選んでください。

### bug

実装・設定・ドキュメント等において、意図した振る舞いや記載内容と異なることが実際に確認された不具合を示します。実装コードの不具合だけでなく、ドキュメントの記載内容が実態と食い違っている場合など、設計・仕様レベルの不整合も対象に含みます。

### design

カラーパレット・アイコン・UI レイアウト等、視覚的なデザイン・アセット制作そのものを目的とするタスクを示します。システム要件やシステムデザインの記述を主目的とする `documentation` とは異なり、成果物が図版・画像・スタイル定義など視覚的要素である点が特徴です。

### documentation

ビジネス要求・システム要件・システムデザイン・ ADR ・ README 等、開発ドキュメントの新規作成や更新そのものを目的とするタスクを示します。すでに方針や仕様が確定している内容をドキュメントへ反映する作業もここに含まれます。

### enhancement

新規機能の追加、または既存機能の拡張を目的とする機能リクエストを示します。

### ops

クラウドリソースのプロビジョニング、スクリプトの実機実行と実データでの動作確認など、コードやドキュメントの作成を伴わない運用作業を示します。

### plan

実装やドキュメンテーションへ反映する内容を確定させるための意思決定・方針検討そのものを目的とするタスクを示します。まだ結論が出ていない論点を Issue 上で議論し、方針を確定させることが目的である点が `documentation` との違いです。方針が確定した後、その内容を開発ドキュメントへ反映する作業は別途 `documentation` を用いて管理します。

### refactor

外部から観測できる振る舞いを変えずに、コードの構造・配置・命名・責務分割などの改善を目的とするタスクを示します。ディレクトリ構成の整理、重複した実装の統合、依存関係の整理などが該当します。コミットの種別 (♻️ `:recycle:`) に対応します。

新しい機能や挙動の変更を伴う場合は `enhancement` を、不具合の修正を伴う場合は `bug` を用います。リファクタリングの途中で挙動の変更が必要になった場合は、挙動の変更を別の Issue に切り出してください。方針の検討そのものを目的とする場合は `plan` を用い、方針の確定後に実施する整理作業を `refactor` で管理します。

### security

セキュリティに関する検討・実装のいずれの段階でも付与しうる、セキュリティ関連の課題・対応を示します。認証・認可、シークレット管理、脆弱性対応などが該当します。

## 状態ラベル

Issue の進行状況に応じて付与・除去します。種別ラベルと組み合わせて使用します。

### draft

とりあえず起票した状態で、具体的な作業に移る前に議論の余地があることを示します。議論を経て、概要・決定事項・受け入れ条件が Issue 本文に反映された時点で除去します。 `detail-issue` スキルを用いた場合は、同スキルが詳細化の完了時に除去します。

### wip

着手・進行中のタスクであることを示します。実装作業に着手した時点で付与し、作業の完了自体は Issue のクローズをもって示すものとします。
(`wip` が付与されているクローズ済みの Issue は、作業完了済みの Issue であることを示します)

### pending

実行は予定されているものの、別のタスクの完了や特定のタイミングを待機しており、現時点で着手できない保留中のタスクであることを示します。

## 横断タグ

種別・状態とは独立した軸で、該当する Issue に併用します。

### ai

Issue の対象がシステムの成果物そのものではなく、 AI エージェント (Claude) の運用・設定・スキル等に対する変更であることを示します。例えば、 Claude Code のスキル追加、 `CLAUDE.md` の方針変更、エージェントの協働手順に関する Issue が該当します。システムの機能追加・修正を目的とする Issue には付与しません。

AI エージェント向けの設定を持たないプロジェクトでは、このタグは不要です。
