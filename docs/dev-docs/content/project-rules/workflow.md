# 開発作業フロー

## 1. このドキュメントの目的

このドキュメントは、本プロジェクトにおける標準的な開発作業フローを定義するものです。
Issue 作成から PR 作成、レビュー、マージまでの手順と、AI へ作業依頼する際の基本フォーマットを示します。

## 2. 標準フロー (Issue -> PR -> Merge)

1. Issue を作成し、背景・目的・スコープ・完了条件を明記する
2. 作業ブランチを `topic/<task-name>` で作成する
3. 実装またはドキュメント更新を行う
   - 作業の中で ADR として記録する価値があると判断できる決定は、 ADR として記録すること (基準・フォーマットは [ADR について](../adr/index.md) を参照)
4. 必要な検証 (静的解析/ユニットテスト) を実行する
5. 変更を論理単位でコミットする
6. ブランチを push し、`develop` 向けに PR を作成する
7. レビューコメントへ対応し、必要な修正を追加コミットする
8. 受け入れ基準を満たしたらマージする

## 3. PR 作成時の必須記載

PR には次を必ず記載する。

- 目的 (なぜこの変更が必要か)
- 変更内容 (何を変えたか)
- 影響範囲 (どこに影響するか)
- テスト観点 (何を確認したか)
- 関連 Issue (`Refs #xx` または `Closes #xx`)

## 4. Issue 作成フォーマット

開発作業が伴う Issue は、以下のセクションを記載することを推奨する。
Issue 作成時点で以下の情報が整理できない場合は、 `draft` ラベルなどつけて概要・要求ベースの記述のみを記載して Issue を作成し、後から議論・詳細化することを想定する。

```markdown
## 背景と目的

<なぜ必要か、達成したい状態>

## スコープ

- <対象1>
- <対象2>

## 非スコープ

- <対象外1>

## 実装方針 (任意)

- <方針1>

## 受け入れ条件

- [ ] <条件1>
- [ ] <条件2>

## 制約 (任意)

- <ブランチ/依存/設計上の制約>
```

## 5. レビュー運用ルール

- 指摘は「再現条件」「問題点」「期待結果」をセットで記載する
- 指摘対象が仕様差分の場合は、関連ドキュメントの該当箇所を明記する
- クリティカルな問題は優先度を明示する
- 指摘解消後は、再レビュー結果を PR 上に明示する

## 6. マージ条件

マージ前に、次を満たしていること。

- CI が成功している
- レビュー指摘が解消されている
- Issue の完了条件が満たされている
- 必要に応じて Issue のチェックリストが更新されている
